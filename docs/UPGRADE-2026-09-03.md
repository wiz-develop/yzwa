## Remaining release gates

- Actual form submission and mailbox delivery were not performed because no approved QA recipient was provided. Confirm both the admin notification and autoresponder in real mailboxes before production approval.
- Log in through the hidden staging login and manually confirm the dashboard, Site Health screen, plugin screen, page editing, and a representative Custom Field Suite field save.
- Compare the staging appearance and content with the intended source. Production has its own `recruit` site and source differences, so a wholesale `test` deployment would be unsafe.

## Production release procedure

1. Obtain fresh production file and database backups and record hashes immediately before release.
2. Create a release branch from `main`; do not merge or deploy the entire `test` tree blindly.
3. Preserve production `recruit`, root files, `.htaccess`, `wp-config.php`, uploads, server plugins, and production-only content.
4. Apply WordPress core 7.1, the listed compatible plugin packages, CFS 2.6.8-wiz.2, and the reviewed theme compatibility changes only.
5. Run the database upgrade, flush caches and rewrites, then verify the hidden login.
6. Repeat public PC/mobile QA, Site Health, REST, loopback, Cron, sitemap, form validation, and approved real-mail delivery checks.
7. Confirm the production PHP/WordPress logs remain free of Fatal, Warning, Deprecated, Notice, and database errors.

## Rollback

1. Put the site into controlled maintenance mode.
2. Restore the fresh pre-release production files, preserving ownership and permissions.
3. Restore the matching pre-release database dump.
4. Clear PHP OPcache, WordPress/plugin cache, and CDN cache.
5. Recheck the public site, hidden login, REST, Cron, and form delivery before ending maintenance.
